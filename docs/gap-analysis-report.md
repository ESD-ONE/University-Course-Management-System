# UCMS — Gap Analysis Report

**Date:** 2026-10-26
**Method:** every gap below was traced to specific source code, migrations, or a frontend
call site — not inferred from documentation or folder structure. Raw evidence (file:line
citations, full endpoint/entity/test inventories) is available on request; this report
states the synthesized finding, impact, and recommendation for each.

**Severity key**: CRITICAL = breaks or fully hides a real, used capability for a role the
system claims to support; HIGH = incorrect/missing enforcement or data integrity risk with
a plausible real trigger; MEDIUM = inconsistency or missing capability with a workaround;
LOW = cosmetic, dead code, or a documented/accepted limitation.

| G-01 | Frontend ↔ academic-structure-service | Department Head authorization | Backend `PermissionResolver` grants a DEPARTMENT-scoped `RoleScopeAssignment` real elevated authority (manage degree programs/courses for the whole department, act on behalf of any lecturer in it) | Angular's only authz primitives are `adminGuard`/`lecturerGuard`, a flat string compare on `ProfileResponse.role`. There is no frontend concept of scope assignments at all — a Department Head account is routed through `lecturerGuard`, sees the same nav as a plain Lecturer, and has no screen to exercise department-wide authority the backend already grants them. | A role the backend fully supports (and the kind-collision bug fix earlier this session confirms is in real use — a "Department Head" custom role exists) is functionally unusable from the UI. | **CRITICAL** | Add a `scopes`/`assignments` field to `ProfileResponse` (or decode the JWT's existing `assignments` claim client-side); add a department-scoped guard/nav variant that surfaces Program Management and Admin Courses (department-filtered) to DEPARTMENT-scope holders, not just ADMIN. | identity-access-service already emits the claim; no backend change needed | Log in as the seeded custom "Department Head" role (or create one via `POST /roles` + `POST /users/{id}/assignments`), confirm via UI which screens are reachable vs. which backend calls succeed if made directly |
| G-02 | identity-access-service (cross-cutting) | Scope-based RBAC as the system's authorization model | `role_scope_assignments`/`assignment_permission_overrides` are fully built, CRUD-able, and embedded in the JWT at login | Outside academic-structure-service's `PermissionResolver`, **nothing reads the `assignments` claim back out**. identity-access-service's own `SecurityConfig` and reference-data-service's `SecurityConfig` both gate purely on the legacy flat `role` via `hasRole()`. The newer layer is write-only/display-only for 2 of the 3 built services. | Admins configuring granular scope assignments today get no effect on Users/Roles/Permissions/Reference-Data endpoints — only on Degree-Program/Course endpoints. Silent, not an error. | **HIGH** | Document this precisely (done, here); decide deliberately whether reference-data-service's writes should also become department-scoped via the same `PermissionResolver` pattern, or whether flat-role ADMIN-gating is the intended permanent model for that service. Do not wire it in without that decision — it changes who can do what. | G-01's frontend work should land first/together, since a backend-only change here with no frontend surface repeats G-01 | Attempt a DEPARTMENT-scoped, non-ADMIN write against `/departments` or `/roles` with a token carrying only that scope assignment; confirm 403 today |
| G-03 | identity-access-service | Role creation | `POST /roles` accepts `{name, kind}` with no uniqueness check on either field | Two roles can share the same `RoleKind` (already happened in production: a custom "Department Head" role collided with the seeded "Lecturer" role on `kind=LECTURER`, causing `NonUniqueResultException` → 403 on `POST /users`) | Confirmed production incident this session; fixed via `findFirstByKindAndDeletedAtIsNullOrderByCreatedAtAsc`, but **that fix lives only on open PR #17, not yet merged to `develop`** — this branch's checkout of `RoleRepository.java` still has the old `findByKindAndDeletedAtIsNull` single-result query | Any further custom role creation before PR #17 merges can reproduce the same 403 on user creation/role change | **HIGH** (open production exposure until merged) | Merge PR #17; separately, add a uniqueness constraint/check on `(name, kind)` or on `name` alone in `createRole` so the root cause (unconstrained creation) is closed, not just the lookup's symptom | None — PR #17 is ready, awaiting manual merge per this session's standing git workflow | Re-run `createRole_duplicateKind_doesNotBreakUserCreation` style test (does not yet exist — see Gap G-03b below) once merged |
| G-03b | identity-access-service | Test coverage for G-03 | `RoleRepository`'s Javadoc now calls the kind-collision scenario "a real case, not hypothetical" | No test exercises it — not for the repository method, not for `createUser`/`updateRole` under a collided-kind scenario | A regression here would not be caught by CI | **MEDIUM** | Add a test: seed two roles with the same `kind`, assert `createUser`/`updateRole` still resolve deterministically (earliest-created) | G-03 | New test in `UserManagementTest`, run under `mvn test` |
| G-04 | identity-access-service | Role change vs. scope assignments | `PUT /users/{id}/role` updates the user's flat `role` only | Does not touch the user's existing `role_scope_assignments` rows, which still reference the old role | A user's flat role and scope-assignment role can silently drift out of sync after any admin-initiated role change, producing inconsistent `PermissionResolver` results in academic-structure-service for that user until an admin separately fixes their assignments | **HIGH** | `updateRole()` should also update (or re-create) the user's GLOBAL assignment to match the new role, same as `createUser()` already does at creation time | G-02's decision on how far scope-based RBAC extends | Change a user's role via `PUT /users/{id}/role`, then `GET /users/{id}/assignments`, confirm whether the GLOBAL assignment's `roleId` changed too (currently: it does not) |
| G-05 | reference-data-service | Department deletion | `DELETE /departments/{id}` is an unconditional soft-delete with zero dependents checking | academic-structure-service's `degree_programs.department_id` and `course_catalog.owning_department_id` are plain UUID references with **no FK, no cross-service check** — deleting a department that's still referenced leaves those rows pointing at a dead department id | A deleted department silently orphans degree programs/catalog subjects; `PermissionResolver.canOnDepartment` would then resolve against a department that no longer "exists" from reference-data's point of view, with undefined UX (departmentId still resolves fine inside academic-structure-service, since there's no live FK check there either) | **HIGH** | Either (a) add a dependents guard to `deleteDepartment` by having reference-data-service query academic-structure-service before allowing the delete (synchronous cross-service check), or (b) accept the current design but document it explicitly as "soft-delete is advisory only across service boundaries" and add a nightly consistency-check job. Do not silently leave this unaddressed, since it is the kind of cross-service referential-integrity gap a Base-service evaluation (see `reference-data-vs-base-analysis.md`) should weigh. | Requires a decision on inter-service consistency strategy (sync check vs. async reconciliation) — a real architectural choice, not a one-line fix | Create a department, create a degree program against it, delete the department via `DELETE /departments/{id}`, confirm the degree program and `canOnDepartment` checks for it still "work" against a now-deleted department |
| G-06 | reference-data-service | Grading Scale / Course Category uniqueness | Neither entity has an `existsBy*` repository method or a DB UNIQUE constraint on any field | Duplicate grading scales / course categories (identical name+content) can be created freely, unlike Faculty/Department which both enforce `code` uniqueness | Data-quality drift over time; a UI that lists these for selection (Reference Data screen) would show indistinguishable duplicates with no way to tell them apart except by `id` | **MEDIUM** | Add a `code` field (or enforce name uniqueness) to both entities, mirroring Faculty/Department's pattern, with a Flyway migration + backfill | None | Attempt `POST /grading-scales` twice with identical `name`, confirm both succeed (currently: they do) |
| G-07 | academic-structure-service | Read/write authorization symmetry | `PermissionResolver.canOnDepartment` gates every **write** on Degree Programs and Courses | `GET /degree-programs/{id}/curriculum` and `GET /courses/{id}/academic-years` have **zero permission check** at the service layer — any authenticated user of any role can read any department's curriculum or any course's year-assignments | A Lecturer in Department A can read full curriculum/offering detail for Department B's programs, despite being blocked from writing to them | **MEDIUM** | Add the same `canOnDepartment(..., "View")` check these two read endpoints' sibling list endpoints already use | None | As a Lecturer scoped only to Department A, call `GET /degree-programs/{idInDeptB}/curriculum`; confirm it succeeds today |
| G-08 | academic-structure-service | Course Catalog CRUD completeness | Course Catalog has GET (list) and POST (create) only | No PUT or DELETE exists anywhere in the codebase for Course Catalog entries — a typo in a subject's code/name or a retired subject can never be corrected/removed, only left in place or worked around by creating a new entry | Data-quality and operational friction; also the most asymmetric CRUD surface in the system (every other entity type has full or near-full CRUD) | **MEDIUM** | Add `PUT /course-catalog/{id}` and `DELETE /course-catalog/{id}` (with a dependents guard against `Course`/`ProgramCourse` references, mirroring the Degree Program delete pattern) | None | `curl -X PUT .../course-catalog/{id}` today returns 405/404 (no mapping exists) |
| G-09 | academic-structure-service | Per-assignment permission overrides | `AssignmentClaim.overrides` (a map of `permissionId → granted`) is parsed out of every JWT | `PermissionResolver.effectiveGrant()` never consults it — only the cached role-baseline grant is checked; the override data is fully round-tripped but inert, by the code's own "Phase 5" comment | An admin who sets a permission override on a specific assignment (via `PATCH /assignments/{id}/overrides`, which succeeds and returns 200) sees **no behavioral change** — a confusing, silent no-op from an API consumer's point of view | **MEDIUM** | Either wire it into `effectiveGrant()` now, or make the `PATCH /assignments/{id}/overrides` endpoint explicitly reject writes (501 or a clear error) until it's load-bearing, so the API doesn't lie about taking effect | None functionally; a product decision on whether Phase 5 is in scope now | Set an override via the endpoint, then exercise the corresponding action with that assignment's token; confirm the override has no effect today |
| G-10 | identity-access-service | Optimistic locking on role-permission updates | `UpdateRolePermissionRequest` carries a `version` field | The service never reads or compares it — Hibernate's own `@Version` column on `Role` still provides real optimistic locking independently, but the DTO's `version` field is pure dead weight that misleads an API consumer into thinking they're sending a concurrency token that matters | Low risk (the real protection mechanism still works), but a confusing/misleading API contract | **LOW** | Remove the unused field from the DTO, or wire it to an explicit pre-check for a clearer 409 message | None | Send two concurrent `PATCH /roles/{id}/permissions` with different `version` values; confirm both succeed (no comparison happens) as long as Hibernate's own version doesn't collide |
| G-11 | identity-access-service | Session lifecycle | `user_sessions` row created on every login | No logout endpoint, no session invalidation, no cleanup job — the table is purely write-only and grows unbounded; JWT validation downstream is fully stateless and never reads it | Not a security gap in itself (stateless JWT validation is a valid design), but the table serves no purpose today and a user cannot invalidate a stolen token short of waiting for its 60-minute expiry | **LOW** | Either implement a real logout (even a simple blacklist-by-session-id check in `JwtAuthFilter`) or remove the table/write if it's not going to be used — currently it's dead infrastructure that looks load-bearing | A real logout feature would need every service's `JwtAuthFilter` to start checking it — a cross-service change | Call `/auth/login` twice, inspect `user_sessions` row count growth, confirm no endpoint ever reads the table |
| G-12 | identity-access-service | User deletion | Soft-delete plumbing (`deletedAt`/`deletedBy`, `findActiveOrThrow` filters) exists on the `User` entity/repository | No endpoint anywhere calls it — the nearest equivalent is `PATCH /users/{id}/status` to INACTIVE/SUSPENDED, which is not deletion (the account still authenticates-rejects via a different code path, but still appears in all admin listings unless filtered by status) | An admin who wants to fully remove a user (e.g. for GDPR-style erasure, or correcting a mis-created account) has no path to do so | **LOW** | Add `DELETE /users/{id}` using the existing soft-delete plumbing, or explicitly document that status suspension is the system's permanent policy instead of deletion | None | `curl -X DELETE .../users/{id}` today returns 404/405 (no mapping exists) |
| G-13 | Frontend | Dead code hygiene | `AcademicStructureService.activateAcademicYear()` and the `/app/degree-programs` route both exist | Neither has a reachable call site in the running application — the activate method is never called (the Academic Calendar screen uses `PUT` with `status:'ACTIVE'` instead), and the route is only ever reached as an embedded tab, never by direct navigation | Not user-facing, but a maintenance hazard — a future developer could reasonably assume either path is live and build on it, or waste time debugging a "route" that nothing links to | **LOW** | Remove the unused method, or wire the Academic Calendar's "activate" action to use it instead of the generic update call (slightly more explicit intent); remove the orphan route or add a real nav link to it if `ProgramManagementComponent`'s embedding is meant to be temporary | None | `grep` the Angular app for call sites of `activateAcademicYear(` and `routerLink="/app/degree-programs"` — both return zero results today |
| G-14 | Frontend | Route-guard granularity | `/app/reference-degree-details` uses `authGuard` only | Every other admin/lecturer feature area uses a role-specific guard (`adminGuard`/`lecturerGuard`); this one doesn't, despite being surfaced only in the lecturer sidebar section and having an admin-side equivalent reached a different way (Program Management tab) | A STUDENT account (or any authenticated role) can navigate directly to this URL and have it render, even though no nav link is ever shown to them | **LOW** | Add the same guard pattern used elsewhere, scoped to whichever roles are actually meant to use this screen | None | Log in as a STUDENT, navigate directly to `/app/reference-degree-details`, confirm it renders today instead of redirecting |
| G-15 | identity-access-service / Frontend | Notification preferences | `PATCH /users/me/notification-preferences` is fully implemented and the Profile screen fully exercises it | No Notification service exists (it's one of the 4 planned-only services) — preferences are persisted with zero downstream effect | None functionally — this is **explicitly disclaimed in the UI itself** ("Not sent yet..."), so it's an honestly-labeled no-op rather than a hidden gap | **LOW** (documented, not hidden) | No action required beyond what's already disclosed; revisit once Notification service exists | notification-service's eventual build | N/A — already verified both the endpoint's persistence and the UI's own disclaimer text |
| G-16 | identity-access-service | Student ID generation | 10-attempt random retry loop (`STU-<year>-<4 random digits>`), not DB-sequence-backed | Under concurrent student account creation, two requests could each pass the `existsByStudentId` check before either commits, producing a narrow race that either silently succeeds with a duplicate (if the DB doesn't enforce uniqueness) or throws after using all 10 attempts (if it does) | Narrow (needs genuinely concurrent creation of 2+ students in the same request-handling window) but real; worsens as the roster of existing IDs for a given year grows and random collisions become more likely near the 10-attempt ceiling | **LOW** | Replace with a DB sequence or `SELECT ... FOR UPDATE`-guarded counter per year, removing the retry-loop's probabilistic failure mode entirely | None | Fire concurrent `POST /users` with `role=STUDENT` from multiple threads against a shared DB connection pool; look for either a 500 after 10 attempts or (if unenforced) two users sharing a `studentId` |
| G-17 | identity-access-service | Login status handling | `/auth/login` rejects both INACTIVE and SUSPENDED users with the same 403 "account not active" message | The rest of the codebase treats these as meaningfully different states (status transitions are visible and distinct everywhere else, e.g. the Users screen's status filter/dropdown) | Minor UX inconsistency — a suspended user and a never-activated user get identical, unhelpful feedback | **LOW** | Differentiate the login error message per status (or confirm this is intentional for security reasons — not leaking account state to a failed-login attempt — and document that reasoning explicitly instead of leaving it unstated) | None | Attempt login as an INACTIVE user and a SUSPENDED user, compare the two 403 response bodies (currently identical) |
| G-18 | Gateway (cross-cutting) | Authentication enforcement model | Every backend service independently validates its own JWT; the Gateway performs zero auth of its own | Consistent and working today across all 3 built services, but it means any **future** service added to the Gateway's routes must remember to add its own `JwtAuthFilter`/`SecurityConfig` — there is no shared enforcement layer that would catch an omission | If one of the 4 planned services is eventually built without copying this pattern faithfully, its endpoints would be open to the internet with zero auth, and nothing at the Gateway layer would catch it | **MEDIUM** (latent, not currently triggered — no planned service exists yet) | Either accept this as the system's deliberate "defense happens per-service" model and document it as a build checklist item for every new service, or centralize a minimal auth check at the Gateway as a backstop (defense-in-depth) before any of the 4 planned services are built | Relevant to planning Enrollment/Assignment-Grading/Notification/Analytics-Reporting's eventual build-out | Code review checklist item for the next service's first PR: confirm a `JwtAuthFilter` equivalent exists before merging routes for it |
| G-19 | academic-structure-service | Security-rule legibility | `SecurityConfig`'s gate-level rules are coarser than actual enforcement; a comment documents that `POST /courses` used to be `hasRole("LECTURER")`-only and was deliberately loosened once service-layer scoping took over | Not a functional bug — service-layer checks are correct and tested — but anyone auditing security by reading `SecurityConfig` alone (as opposed to also reading `PermissionResolver`/the services) would underestimate who can call these endpoints, since the gate says "any authenticated user" | Documentation/legibility risk for future audits, not a live vulnerability | **LOW** | Add a short pointer comment in `SecurityConfig` itself: "see `PermissionResolver` for the real per-endpoint decision on Degree Programs/Courses" | None | N/A — a documentation-only finding |
| G-20 | System-wide | The 7-microservice architecture | 3 of 7 planned services are built (identity-access, academic-structure, reference-data) + the Gateway | Enrollment, Assignment-Grading, Notification, and Analytics-Reporting have **zero code** — schemas are reserved (`infra/init-schemas.sh`) but contain no tables. This is the single largest "gap" in the system by scope, fully detailed in `system-architecture-analysis.md` §1 and referenced here as the scope anchor for every other finding above. | There is no student-facing capability in the system at all today (no enrollment, no grades, no notifications, no reports) — the Students role exists only as a login + Dashboard + Profile shell | **CRITICAL** (by design/roadmap — not a bug, but the defining scope boundary for this whole analysis) | No action within this audit's scope — see `reference-data-vs-base-analysis.md` for how this boundary affects the Reference-Data-vs-Base evaluation, and treat any future build-out of these 4 services as its own project, informed by the patterns (and gaps) documented across this report | All of the above, as precedent for how auth/validation/soft-delete/audit conventions should be replicated | Confirmed via `grep -r` across every `pom.xml`/`.java` in `services/` for the 4 missing services' expected package names — zero hits |

## Summary by severity

- **CRITICAL (2)**: G-01 (Department Head role invisible on frontend), G-20 (4 of 7 services don't exist — the scope boundary itself)
- **HIGH (4)**: G-02 (scope-RBAC only wired into 1 of 3 services), G-03 (role kind-collision, fix unmerged), G-04 (role-change/scope-assignment drift), G-05 (Department delete has no cross-service dependents guard)
- **MEDIUM (6)**: G-03b, G-06, G-07, G-08, G-09, G-18
- **LOW (9)**: G-10, G-11, G-12, G-13, G-14, G-15, G-16, G-17, G-19
